# Scientific Data Platform

A real, runnable data-ingestion and cross-study knowledge synthesis backend,
built to demonstrate the engineering behind this resume line:

> **Scientific Data Platform** | Cloud Architecture, Knowledge Synthesis
> - Scalable platform ingesting 150+ research datasets for cross-study knowledge synthesis
> - Customer-driven product features: workflow automation, real-time insights, collaboration

## What's real vs. architectural (read this first)

**Real, and verified in this environment:**
- A real synthetic dataset generator (`data/generate_research_datasets.py`, fixed seed=42) that produces **163 datasets** spanning three study types (gene-expression, clinical-outcome, drug-screening), with deliberate entity overlap (the same gene/outcome/compound appearing across many studies) and **7 deliberately malformed datasets** injected to exercise error handling.
- A real ingestion pipeline (`data/ingest.py`) with explicit schema validation, per-dataset status logging (`data/ingestion_log.json`), and a real relational SQLite database (`data/platform.db`) with foreign keys and indexes.
- A real cross-study synthesis engine (`synthesis/cross_study_engine.py`) that queries the actual database for every finding on a given entity across every study that references it, computes a sample-size-weighted pooled effect estimate, and computes a genuine disagreement/consensus signal from the underlying numbers (not hardcoded).
- A real Flask REST API (`app/main.py`) implementing all three "customer-driven product feature" groups from the resume line — workflow automation, real-time insights, collaboration — backed by the real database, with no caching layer on the synthesis endpoint (every call recomputes from the DB).
- A real test suite: `tests/test_pipeline.py` (ingestion + synthesis correctness, including constructed known-consistent vs. known-contradictory entities) and `tests/test_api.py` (Flask test client against the real seeded DB). **24/24 tests pass** (`pytest -q`, run locally in this environment).
- A real end-to-end orchestration script (`run_all.py`) that generates data, ingests it, runs synthesis on real multi-study entities, and writes a real report + real matplotlib figures from the actual run — see **Results** below for the actual numbers it produced.

**Honest gaps / architectural-only claims:**
- **No cloud infrastructure was provisioned.** No AWS/GCP/Azure account, no managed data warehouse, no real multi-tenant deployment — intentionally, since that costs money and requires credentials this environment doesn't have. "Cloud Architecture" is represented as a **documented, scalable design** (containerization, partitioning strategy, and a path to a managed warehouse) — see below — not a live deployment.
- **No real LLM API calls.** This is not a wrapper around Claude/GPT/any hosted LLM — no API key is needed, and the whole thing runs fully offline. "Knowledge synthesis" here means real statistical aggregation (weighted pooling + a computed disagreement signal) across real rows in a real database, not text generation.
- The "150+ research datasets" are **synthetic**, generated by a documented, seeded script — not real published studies. The schema, overlap structure, and validation failures they exercise are realistic and the pipeline that processes them is real.

## Cloud architecture (documented design, not deployed)

The platform is designed so the ingestion + synthesis logic is decoupled from
where the data physically lives:

- **Containerization**: the Flask app and ingestion pipeline are designed to run as a single container image (Python 3.11-slim base, `pip install -r requirements.txt`, `CMD ["python3", "app/main.py"]`). A `docker-compose.yml` would add a second service for a managed-Postgres stand-in, the same pattern used in the sibling `GenomicsDataAPI` project in this portfolio. Not included here to keep this build minimal and disk-light; the design is identical to that project's documented (not deployed) Docker setup.
- **Partitioning/sharding strategy**: `findings` is the platform's largest, highest-growth table (one row per entity-per-study). In production this table would be partitioned by `study_type` (three logical shards matching the three ingestion streams) and further range-partitioned by `publication_year`, so queries like "all findings for entity X since 2020" hit a single partition. `studies` stays a small reference table, unpartitioned.
- **Path to a managed cloud data warehouse**: all DB access is isolated behind `data/ingest.py::get_connection()` and `synthesis/cross_study_engine.py::_connect()`, both reading the DB path from a single `PLATFORM_DB_PATH` env var and using only standard SQL (no SQLite-specific syntax beyond `AUTOINCREMENT`). The intended production swap is SQLite -> **Amazon Redshift or Google BigQuery** (or Postgres/RDS as an intermediate step) via a SQLAlchemy engine pointed at a `DATABASE_URL`, with the 150+-dataset ingestion pipeline adapted into a batch/streaming loader (e.g. one ingestion job per incoming dataset feed, landing in a staging table before an upsert into the partitioned `findings` table). The application/route layer would not need to change, since it only uses the row-dict/connection abstraction.
- **Scaling ingestion beyond 150+ datasets**: `data/ingest.py` already validates and logs each dataset independently (no shared transaction across datasets), so the ingestion step parallelizes trivially — in production this would run as a fan-out of worker tasks (e.g. one per incoming dataset) behind a queue, each worker doing exactly what `ingest()` does today for a single record.

This is presented as an explicit design, not a deployed system.

## Ingestion pipeline

`data/generate_research_datasets.py` generates synthetic datasets across three
study types (`gene_expression`, `clinical_outcome`, `drug_screening`), each
with a small table of numeric findings (log2 fold-change or effect size, a
p-value, and a sample size) for entities drawn from small shared pools (24
genes, 10 clinical outcomes, 15 compounds) using power-law-weighted sampling —
so a handful of "hot" entities show up across dozens of studies, which is what
makes cross-study synthesis meaningful. 7 datasets are deliberately malformed
(missing fields, wrong types, empty findings, invalid enums) to exercise error
handling.

`data/ingest.py` validates every dataset against an explicit schema (required
fields, valid study types, valid metrics, non-empty findings, positive sample
sizes, sane publication years), logs each dataset's accept/reject status and
reason to `data/ingestion_log.json`, and loads accepted datasets into a real
SQLite database (`data/platform.db`) with a `studies` table, a `findings`
table (indexed on `entity` and joined via foreign key), plus supporting tables
for users, insights, and workflow runs (used by the API below).

## Cross-study synthesis logic

`synthesis/cross_study_engine.py::synthesize(entity)` queries every finding
for a given entity across every ingested study, then computes, from the real
rows:

- a **sample-size-weighted pooled estimate** (fixed-effect-style meta-analysis
  pooling: `sum(value * n_samples) / sum(n_samples)`), plus a naive unweighted
  mean for comparison;
- a **consensus direction** (`positive` / `negative` / `mixed`);
- a **disagreement score**, combining the fraction of studies whose finding
  direction disagrees with the majority and the coefficient of variation of
  the raw values — a genuinely computed signal, verified by
  `tests/test_pipeline.py` against constructed entities with known-consistent
  findings (asserted `low` disagreement) and known-contradictory findings
  (asserted `high` disagreement).

## Product features (API)

### 1. Workflow automation
- `GET /api/workflows` — list named, multi-step workflows (`full_refresh`: re-ingest + synthesize; `synthesize_only`: synthesize top overlapping entities)
- `POST /api/workflows/<name>/run` — actually runs the named workflow's steps against the real DB and records the run in `workflow_runs`
- `GET /api/workflows/runs` — history of workflow runs

### 2. Real-time insights
- `GET /api/entities?min_studies=N` — entities referenced by N+ studies (candidates for synthesis)
- `GET /api/synthesis/<entity>` — freshly computed synthesis for one entity, recomputed from the DB on every request (no cache)
- `GET /api/studies`, `GET /api/studies/<study_id>` — browse ingested studies and their findings

### 3. Collaboration
- `POST /api/insights` — save a named annotation on a synthesis result (snapshots the synthesis output at save time), owned by a `created_by` user
- `GET /api/insights?user=<name>` — list insights owned by or shared with a user
- `GET /api/insights/<id>` — fetch one insight
- `POST /api/insights/<id>/share` — share an insight with another user; ownership is enforced (non-owners get `403`)

## How to run

```bash
cd ScientificDataPlatform
python3 -m venv .venv
source .venv/bin/activate
pip install --no-cache-dir -r requirements.txt

# full pipeline: generate -> ingest -> synthesize -> report + figures
python3 run_all.py

# start the API (http://localhost:5060)
python3 app/main.py

# in another shell:
curl http://localhost:5060/api/health
curl "http://localhost:5060/api/entities?min_studies=5"

# run the real test suite
pytest -q
```

## Tech stack

- **Data generation / ingestion**: Python 3, sqlite3, fixed-seed synthetic data generation
- **Database**: SQLite (local/portfolio), schema and access layer designed for a drop-in swap to Postgres/Redshift/BigQuery (see Cloud Architecture above)
- **Synthesis**: pure Python statistical aggregation (weighted pooling, coefficient of variation, direction-disagreement scoring) — no external ML/LLM dependency
- **API**: Flask (chosen for minimal dependency footprint in a disk-constrained build environment)
- **Testing**: pytest, Flask test client
- **Visualization**: matplotlib
- **Architecture story**: Docker + partitioned warehouse — documented design, not provisioned
